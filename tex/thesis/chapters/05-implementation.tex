\chapter{Implementation}
\label{chap:implementation}

This chapter describes the system architecture, historical dataset builder,
design-cycle corrections, and evaluation instrumentation. Appendices~\ref{appendix:impl-detail}
to~\ref{appendix:impl-eval-instruments} document technology choices, module
layout, model configurations, artifact format, runtime services, and deployment.
This separation keeps the implementation reproducible and auditable under the
Design Science Research framing \cite{hevner2004design,peffers2007design}.

\section{System Architecture Overview}
\label{sec:impl-architecture}

Figure~\ref{fig:architecture} shows the organization. Three properties affect the
research results; Appendix~\ref{appendix:impl-detail} gives the component
inventory and language choices.

\begin{enumerate}
  \item \textbf{One shared definition of every feature.} The training code and the runtime scoring service read the same versioned feature definitions. A feature computed one way during training and another way at scoring time would silently invalidate every reported metric, because the model would be evaluated on one function of the data and deployed on another.

  \item \textbf{Training and scoring are strictly separated.} Models are never fitted during normal application use: the training pipeline exports versioned model files that are promoted into a staged bundle, and the scoring service loads only these. This is what allows Chapter~\ref{chap:demonstrator} to be read as evidence about the evaluated model.

  \item \textbf{The unit of analysis is a single repository,} scored independently; the dependency inventory to grade is an external input, for the reasons set out in Section~\ref{sec:background-supply-chain-security}.
\end{enumerate}

\section{Historical Dataset Builder}
\label{sec:impl-dataset-builder}

The historical builder is a Python package under
\texttt{app\sslash training\sslash maintenance\_dataset}. It converts a
repository seed and GH Archive files into an inspectable, leakage-controlled
dataset. Separate modules handle ingestion, event parsing, features, and labels
for independent testing. Appendix~\ref{sec:impl-dataset-modules} documents the
layout, and Appendix~\ref{sec:impl-dataset-quality} the quality report.

The code enforces the observation-time/future-window boundary. Each snapshot has
a feature window for the year before \(t\), a previous window for the preceding
year, and a label window for the twelve months after \(t\). Features use events
at or before \(t\); labels use events strictly after it.

The label implements the thesis-specific two-of-four rule from
Section~\ref{sec:method-definitions}. It counts distinct human-commit months,
future contributors, releases or package publications, and merged pull requests.
A repository is maintained only when it is not archived or deleted within the
horizon and at least two conditions hold. If the dataset-wide archive horizon
does not cover the full label window, \texttt{future\_window\_incomplete} is set
and the row remains unlabeled. Section~\ref{sec:impl-label-completeness}
describes a correction to this coverage horizon.

Human-versus-bot attribution is applied during both feature and label computation. Commit and contributor counts use an actor filter that excludes automated accounts, so that bot-driven activity does not inflate maintenance evidence. The same reasoning motivates the cautious treatment of responsiveness signals in the methodology, where automated responses are known to distort interaction metrics \cite{hasan2023firstresponse}; those features are reconstructed proxies and are not bot-filtered (Section~\ref{sec:method-feature-engineering}).

The export step produces two outputs with different purposes. The training snapshot file is the dataset itself --- one row per observation snapshot, in the table layout the training notebook already expects (Section~\ref{sec:method-dataset-construction}). The repository feature cache stores, for each repository, the most recent observation-time feature row, with diagnostic-only fields such as \texttt{repo\_archived\_at\_obs} removed. This cache is what later allows the runtime backend to score a previously seen repository in the richer full-history regime rather than the cold-start regime.

The formative review produced two builder refinements. Raw counts such as
absolute open issues, which can also be high for healthy projects, were replaced
with relational and trend-based variables. The builder also resolves one primary
package-to-repository link so mirrors do not make an active project appear
inactive (Appendix~\ref{sec:impl-feature-refinement}). The second refinement
corrected label completeness.

\label{sec:impl-label-completeness}
\textbf{The label-completeness correction.} This correction changes only which
rows qualify as labeled examples. The prediction objective, window
\((t, t + 12\text{ months}]\), two-of-four rule, model, and target are unchanged.

A row is labeled only when its future window is fully covered
(Section~\ref{sec:method-leakage-prevention}). The initial implementation used
each repository's last event as its coverage end. This proxy is correlated with
the outcome: a repository that falls quiet has no late events, so later snapshots
were discarded as ``incomplete'' even when the archive covered their windows.
Inactive repositories were therefore under-represented among labeled positives.

The corrected gate uses a dataset-wide archive horizon: either the latest event
across all repositories or the cutoff supplied by
\texttt{-{}-coverage-end}. The orchestration script defaults to the latest day
of complete hourly GH Archive coverage. Silent repositories inside the horizon
can now be labeled inactive; rows extending beyond available data remain
unlabeled. The \texttt{repo\_silent\_before\_horizon} diagnostic identifies
labelable rows whose own last event precedes the horizon, making the rescued
share inspectable in the quality summary. This aligns the implementation with
the leakage rule and removes the selection effect that reduced the labeled
inactive population.

\section{Model Training and Evaluation Instrumentation}
\label{sec:impl-models}

Both regimes implement Logistic Regression and a feedforward neural network from
first principles, and XGBoost through its library \cite{chen2016xgboost}. The
first two remain dependency-light and inspectable. All families share the
dataset, time-aware split, calibration, and evaluation code.
Appendix~\ref{sec:impl-from-scratch} gives the configurations, and
Appendix~\ref{sec:impl-artifacts} the artifact format.

All families use the same post-processing. A classifier may rank repositories
correctly while over- or understating inactivity probability. A separate
calibration step maps raw scores to observed frequencies
(Section~\ref{sec:background-ml-basics}).

The \emph{histogram} calibrator groups validation predictions into probability
bins, assigns each a smoothed empirical inactivity rate, and enforces a monotonic
mapping. Unlike logistic (Platt) scaling, it assumes no parametric shape. This
suits model families with different distortions. Its bin boundaries and rates
are also stored in the model file and replayed at inference. The calibrator uses
validation data, never test data, so calibration metrics remain
out-of-sample.\kiref{Claude Opus 5/4}

Inference uses piecewise-linear interpolation between populated bins. A flat
lookup would collapse every raw score in a bin to one value and create ties in
the ranked view. Interpolation preserves raw-score order and empirical
calibration. Monotonic bin rates keep the mapping monotonic.

A decision threshold is then selected on the calibrated validation predictions by maximizing the F1 score, and the evaluation module computes the reported metrics (Section~\ref{sec:method-evaluation-strategy}) on the test set.

The first complete run motivated two additional evaluation instruments.

Most test rows describe repositories already quiet before \(t\). The
\emph{slice evaluation} checks whether this easy majority dominates the
aggregate result. It recomputes metrics by popularity, history regime, and
activity at \(t\), so a strong majority cannot hide a weak subgroup.
Appendix~\ref{sec:impl-slice-evaluation} documents the included and excluded
dimensions. Section~\ref{sec:results-baselines} reports the resulting split
finding.

The \emph{repository-disjoint split} addresses recurrence across the date-based
split. It confines all ten quarterly snapshots of a repository to one partition,
testing generalization to unseen repositories
(Section~\ref{sec:results-robustness}).

The two instruments differ in kind. The slice evaluation is a re-analysis: it
re-scores the predictions of the already fitted model. The repository-disjoint
split is a separate training run, which refits preprocessing, model, calibrator,
and decision threshold on its own partitions and leaves its test rows untouched
until every fitting decision is made. Neither changes the staged artifacts or the
headline metrics, because the reported run keeps the date-based split.
Appendix~\ref{appendix:impl-eval-instruments}
documents their mechanics.\kiref{Claude Opus 5/4}

\section{Reproducibility of the Evaluated Artifact}
\label{sec:impl-deployment}

Three mechanisms make each result traceable to a fixed model and dataset.

All training runs through
\texttt{notebooks\sslash oss\sdash maintenance\sdash training\sdot ipynb}, the
only writer of model files. \texttt{npm run ml:train} executes it
non-interactively (Appendix~\ref{sec:impl-training-orchestration}), so reported
results use the documented path. Each artifact records ordered feature names,
parameters, calibration bins, decision threshold, feature-set version, and
dataset hash (Appendix~\ref{sec:impl-artifacts}). The hash in
Appendix~\ref{sec:method-reproducibility} verifies rebuilt data against the
evaluated dataset.

Artifacts are not deployed automatically. The staging command requires every
model's ROC-AUC not to drop and its Brier score not to exceed the configured
tolerance relative to the deployed baseline
(Appendix~\ref{sec:impl-staging}). Dataset hash and model version link the
demonstrator output in Chapter~\ref{chap:demonstrator} to the evaluated model in
Chapter~\ref{chap:evaluation}.

The scoring service (Appendix~\ref{sec:impl-scoring-service}), backend
(Appendix~\ref{sec:impl-backend}), frontend
(Appendix~\ref{sec:impl-frontend}), and deployment
(Appendix~\ref{sec:appendix-impl-deployment}) consume these artifacts. They
provide engineering context; no reported result depends on them.
