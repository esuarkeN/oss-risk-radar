\chapter{Background}
\label{chap:background}

This chapter covers software supply-chain security, open-source project health,
metric limitations, and the machine-learning concepts used for inactivity-risk
scoring.

\section{Software Supply-Chain Security}
\label{sec:background-supply-chain-security}

Software supply-chain security addresses insufficiently controlled or
verifiable artifacts, build processes, dependencies, and distribution channels
\cite{souppaya2022ssdf,slsa2025spec}. The NIST Secure Software Development
Framework includes the acquisition and maintenance of well-secured components
\cite{souppaya2022ssdf}. SLSA defines integrity and provenance requirements for
artifacts and build processes \cite{slsa2025spec}. The NIST requirement motivates
examining upstream maintenance in addition to dependency versions.

Open-source licenses permit use, modification, and redistribution under criteria
specified by the Open Source Initiative \cite{osiOpenSourceDefinition}. These
freedoms enable broad reuse, while downstream users depend on external
maintainers and public infrastructure. Upstream activity is therefore relevant
to downstream risk assessment. Inactivity-risk scoring estimates whether public
repository signals warrant monitoring, replacement planning, or manual review;
it does not assess a dependency's overall security.

The unit of analysis is one repository. Software-composition-analysis tooling
provides the dependency inventory as an external input
(Section~\ref{sec:impl-architecture}).

\section{Open-Source Sustainability and Project Health}
\label{sec:background-oss-health}

Open-source sustainability describes whether a project can continue to provide value and maintain its software over time. Project health is commonly assessed through observable indicators such as activity, responsiveness, contributor participation, and release behavior \cite{goggins2021transparent}, for which the CHAOSS project provides standardized metrics models \cite{chaossStarterProjectHealth}.

Repository activity includes commits, releases, tags, issues, pull requests, and
contributors observed through public platforms and package metadata. Prior
research uses revision activity and project attributes to study open-source
project survival \cite{robinson2022survival}. These signals support the 12-month
inactivity prediction developed here.

OpenSSF Scorecard supplies a second category of signals through automated
security-related checks that describe repository configuration and security
posture \cite{zahan2023scorecard}. Section~\ref{sec:related-security-practice}
explains why these signals remain separate from the inactivity model.

Project health remains broader than any single metric
\cite{goggins2021transparent}. The inactivity-risk score is therefore a limited
operational signal for dependency triage.

Appendix~\ref{appendix:health-indicators}
(Table~\ref{tab:background-health-indicators}) groups the signals into commit
activity, contributor activity, issue and pull-request activity, release
activity, age and popularity, and security practice. Section~\ref{sec:method-feature-engineering}
defines the model features.

\section{Metric Pitfalls and Limitations}
\label{sec:background-metric-pitfalls}

Repository metrics can be misleading without context
\cite{yehudi2023contextfree}. Their meaning depends on project type, maturity,
governance, and maintenance style.

A low commit count can indicate reduced maintenance or a stable project needing
few changes. A high issue count can represent an active community or an
unresolved backlog. Context-free indicators are therefore insufficient on their
own \cite{yehudi2023contextfree,kalliamvakou2016perils}. The model combines
multiple signals and evaluates them empirically.

Automated replies can distort time-to-first-response in pull-request workflows
\cite{hasan2023firstresponse}. Human and automated activity should therefore be
separated where possible (Section~\ref{sec:related-responsiveness}). The commit
and contributor signals use a human-actor filter
(Appendix~\ref{appendix:feature-reference}), whose effect is measured in
Appendix~\ref{appendix:bot-ablation}. The responsiveness features remain
unfiltered reconstructed proxies.

Public repository data may omit development on other platforms, releases outside
the observed repository, private maintenance channels, or ambiguous
package-to-repository mappings \cite{kalliamvakou2016perils}. The results cover
only publicly observable activity.

The inactivity label consequently records the absence of selected public
activity signals within a defined horizon. It is a measurable proxy for elevated
maintenance risk, not a declaration of project death or abandonment.

\section{Machine Learning Basics for Tabular Risk Scoring}
\label{sec:background-ml-basics}

The prediction task is binary classification: at observation time \(t\) the model estimates the probability that a repository becomes inactive in \( [t, t + 12\ \text{months}] \) from features derived from public metadata and activity. Because inactivity is closely related to recent activity, a recency baseline --- ranking repositories by the time since their last observed commit or release --- serves as the reference point.

The recency baseline solves the same forward-looking task as the model. Both use
only repository state at \(t\) and are scored against
\( (t, t + 12\ \text{months}] \). The baseline extrapolates one variable: a
repository silent for a long time is predicted to remain silent. The learned
model combines many variables. This is a strict like-for-like comparison because
the label is activity-derived and prolonged silence predicts future silence.
Any improvement over the baseline cannot be obtained from the last commit date
alone.\kiref{Claude Opus 5/2}

Logistic regression serves as an interpretable probabilistic baseline, while tree-based models such as gradient boosting capture the non-linear feature interactions common in tabular repository metadata \cite{james2021islr,breiman2001randomforests,friedman2001greedy}.

The evaluation measures \emph{discrimination} and \emph{calibration}.
Discrimination asks whether repositories that become inactive rank above those
that remain active. Calibration asks whether a predicted probability such as
\(0.8\) corresponds to an observed inactivity frequency of roughly \(80\%\).
A model can perform differently on the two criteria, so both are reported.

Discrimination is measured by \textbf{ROC-AUC}, the area under the receiver
operating characteristic curve. It is the probability that a randomly chosen
inactive repository receives a higher score than a randomly chosen active one.
A value of \(0.5\) corresponds to random ordering; \(1.0\) ranks every inactive
repository above every active one. ROC-AUC depends on score \emph{order} and requires no
decision threshold, which suits a ranked triage view. Under strong class
imbalance it can appear optimistic, and the area under the precision-recall curve
is more informative when the negative class dominates
\cite{saito2015precision}. That condition does not hold for the full test set,
whose majority class is inactive
(Section~\ref{sec:method-evaluation-strategy}), but it does hold for the subset of
repositories still active at the observation date, for which
\textbf{average precision} is therefore reported alongside ROC-AUC
(Section~\ref{sec:results-precision-recall}).

Calibration is measured by the \textbf{Brier score} and the \textbf{expected
calibration error (ECE)}. The Brier score is the mean squared difference between
the predicted probability and the outcome, coded as \(1\) for inactive and \(0\)
for active. Lower values are better. Predicting the base rate \(\bar{p}\) for
every repository yields \(\bar{p}(1-\bar{p})\), so a lower score indicates skill
beyond that reference.

ECE groups predictions into probability bins and averages the absolute
difference between each bin's predicted probability and observed outcome
frequency. It expresses
miscalibration in the units of the score. Calibration is required to interpret a
score as a probability, for example as a one-in-four chance of inactivity within
a year, when planning replacement \cite{niculescu2005probabilities}. Appendix~\ref{sec:method-metric-definitions}
defines these metrics, log loss, precision, recall, F1, and the composite quality
score.

All metrics use a \emph{held-out test set} excluded from model fitting and
calibration. The split is time-aware, so later periods cannot influence model
development for earlier ones. This matches the use of historical information to
predict future inactivity.\kiref{Claude Opus 5/2}
